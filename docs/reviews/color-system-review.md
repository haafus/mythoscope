# Разбор системы цветов категорий (бэк + фронт)

Аудит того, где цвета категорий генерируются, хранятся, передаются и
используются, со всеми местами хранения, дублями и нелогичностями.
Состояние на коммит `709c956`. Это аналитический документ — код по нему ещё
не менялся.

## 1. Где генерируются (бэк, build-time)

Единственный генератор — `corpus/utils.py:93` `get_tradition_color`:

```python
_used_colors: set[str] = set()
_tradition_colors: dict[str, str] = {}

def get_tradition_color(tradition):
    with _color_lock:
        if tradition in _tradition_colors:
            return _tradition_colors[tradition]
        while True:
            color = f"#{random.randint(0, 0xFFFFFF):06X}"   # рандом по всему RGB
            if color not in _used_colors:
                ...
```

Вызывается ровно из одного места — `corpus/builder.py:153` (`_update_traditions`),
при `mytho corpus`. То есть цвет традиции рождается **на сборке корпуса**,
случайным образом.

## 2. Где хранятся (все места)

| Место | Что | Жизнь |
|---|---|---|
| `outputs/corpus/traditions.json` → `traditions[x].color` | источник правды при сервинге | на диске, перезаписывается каждой сборкой |
| `_tradition_colors` / `_used_colors` (модульные глобалы `corpus/utils.py`) | транзитный кэш + дедуп на время процесса сборки | в памяти, стартует пустым |
| **Каждая строка catalog-ответа** `documents[i].color` | копия цвета традиции на *каждом* документе | в ответе `/api/corpus/catalog` |
| `state.traditionInfo` (фронт, `core.js:13`) | копия `/traditions` в памяти SPA | на время сессии |
| `el._traditionColors` (`chart.js:48`) | массив цветов под Plotly-трейсы | на DOM-элементе графика |

## 3. Как передаются (две параллельные дорожки одного и того же)

Один и тот же цвет традиции уезжает на фронт **двумя независимыми путями**:

- `/api/corpus/traditions` → `loadTraditionInfo()` (`core.js:165`) → `state.traditionInfo`;
- `/api/corpus/catalog` → `get_catalog_documents` **денормализует** цвет в каждую
  строку (`services/corpus.py:29`), фронт читает `docs[0].color`.

## 4. Где используются (фронт)

- **Деревья традиций:** `tree-traditions.js:17`, `tree-sources.js:31` → CSS-переменная
  `--tradition-color` (из `docs[0].color`).
- **Corpus info-dot:** `page-corpus.js:70` → `--book-color` (из `doc.color`).
- **Geography маркеры:** `page-geography.js:69,130` → `--point-color`
  (из `traditionInfo`, через `isValidColor`).
- **Embeddings scatter/distribution:** `page-embeddings.js:22` `getColorMap` →
  `chart.js` (`marker.color`, + `dimColor` для невыбранных в `chart-color.js`).
- **Граф-узлы (другая «категория»):** `page-graphs.js:13` `GRAPH_CATEGORY_COLORS`
  (Character / Location / Epoch / Other). Бэк проставляет строку `Category`
  (`graph_generator.py:136,238`), цвет назначает только фронт. Имена совпадают —
  рассинхрона нет.
- **Score-классы** (`app.css:1158`) — отдельная семантика (релевантность),
  самосогласована, к цветам категорий не относится.

## 5. Дубли

1. **Двойная транспортировка цвета традиции** — `/traditions` и денормализация
   в `/catalog` несут одно и то же. Фронт держит обе копии (`traditionInfo` и
   `docs[].color`) и использует то одну, то другую.
2. **Денормализация на каждый документ** — цвет дублируется N раз (по числу книг),
   хотя реально читается только `docs[0].color` на группу.
3. **Трижды повторённое извлечение** `docs[0] && docs[0].color ? … : "#6b7280"` —
   `tree-traditions.js:17`, `tree-sources.js:31` (плюс вариант в `page-corpus.js:70`).
4. **Второй, конкурирующий палитра-набор** — `page-embeddings.js:23` зашивает
   categorical-палитру tab10 `["#1f77b4", …]` как fallback. Это отдельная цветовая
   схема: если у традиции вдруг нет цвета, scatter раскрасит её **иначе**, чем
   деревья/гео.

## 6. Нелогичности и неэффективности алгоритма

1. **Недетерминированность.** `random.randint` без сида и без привязки к имени
   традиции → **каждая пересборка `mytho corpus` перетасовывает все цвета**
   (config-дерево цвета не хранит, старый `traditions.json` не читается).
   Противоречит цели «воспроизводимый пайплайн». Тест `test_corpus_utils`
   это маскирует — проверяет стабильность только *внутри одного процесса*.
2. **Цвет — не функция традиции.** Его нельзя пересчитать, поэтому приходится
   хранить и гонять по сети. Детерминированный `hash(name) → hue` снял бы и
   хранение, и обе транспортные дорожки (фронт смог бы считать цвет сам).
3. **Полный RGB-диапазон без контроля контраста.** Может выпасть
   near-white / near-black / кислотный / неотличимый от соседнего. UI пастельный,
   а маркеры — произвольно-насыщенный рандом. Дедуп только по точному hex —
   визуально близкие цвета не разводятся.
4. **Пять-шесть разных дефолтов «неизвестного цвета»** вместо одного:
   `#6b7280` (tree×2, corpus, CSS×2), `#334155` (geography JS+CSS),
   `#555` (`getTraditionColor`), `#888888` (`chart.js:48`), `#94a3b8` (CSS:682),
   `#aaaaaa` (graphs:101). Одна и та же ситуация «цвета нет» выглядит по-разному
   в разных разделах.
5. **Избыточная concurrency-обвязка.** `_color_lock` + глобальные сеты рассчитаны
   на параллельные вызовы, но единственный вызыватель (`_update_traditions`)
   работает строго последовательно. Лок сейчас не нужен.
6. **Глобальное мутабельное состояние** (`_tradition_colors`) в utils-модуле —
   стартует пустым каждый процесс, никакой пользы при сервинге (там цвет уже из
   json), только источник тестовой нестабильности.

## 7. Отдельная палитра `REGION_COLORS` — это НЕ система цветов категорий

В разделе Motifs фронта живёт **вторая, независимая** цветовая система, и её нельзя
путать с описанной выше (цвет традиции). `REGION_COLORS`
(`server/web/assets/page-motifs.js:1046`) — статический словарь «имя макро-региона →
hex», а `regionColor(name, i)` возвращает цвет по имени либо запасной из
`_FALLBACK_COLORS`.

```js
const REGION_COLORS = {
  "Europe": "#4f7096", "Near East": "#c9873f", "Central Asia": "#8a7f4e",
  "South Asia": "#6f9a5a", "East Asia": "#b45c4b", "Southeast Asia": "#4f9d8a",
  "Asia": "#6f9a5a", "Siberia": "#5f8aa0", "Arctic": "#8fb0c4", "Africa": "#9c6a94",
  "North America": "#7d84b8", "Mesoamerica": "#c47a5a", "Mesoamerica & Caribbean": "#c47a5a",
  "South America": "#bd9a43", "Caribbean": "#59a3b0", "Oceania": "#3f9e93", "—": "#b7c0c7",
};
```

Чем принципиально отличается от системы §1–§6:

- **Другая сущность.** Красит **макро-регион аттестации мотива** (поле `region` на
  записи мотива — провенанс Berezkin/ATU/TMI, «где встречается мотив»), а не
  **традицию**. Используется только в обзорных барах распространения и в аккордеонах
  аттестаций по типам источников (`page-motifs.js:1138,1317` и др.), чтобы регион
  читался одним цветом во всех этих местах.
- **Статическая и детерминированная** — задана вручную в коде, не генерится
  `random.randint` (не имеет ни одной из проблем §6: не тасуется на пересборке, цвета
  подобраны в общий приглушённый тон), не хранится в json и не гоняется по сети.
- **Свой словарь имён.** Ключи (`Near East`, `Central Asia`, `Southeast Asia`,
  `Caribbean`, общий `Asia`, `—`) **не совпадают** ни со значениями `major_tradition`
  (`Indo-European`, `Abrahamic`…), ни один-в-один с 12 научными макро-ареалами
  (`macro-area-facets.md`). Комментарий в коде честно называет это «echoes the
  12-geographic-layer mockup» — перекликается визуально, но это не тот же источник
  правды.
- **Свой дефолт «нет региона»** — `"—" → #b7c0c7` (не `CATEGORY_NONE` из §«Обновление»).

Итого — это **третья классификация** рядом с `major_tradition` (дерево традиций) и 12
макро-ареалами (научная гео-ось традиции); все три параллельны и не тождественны.
Сводить `REGION_COLORS` с системой цвета традиции не следует: они на разных сущностях
(мотив против традиции) и с разными словарями. Единственное, что стоило бы (на
будущее) — привести имена регионов мотива к 12 макро-ареалам, если гео-ось будет
продакшенизирована, чтобы три словаря наконец сошлись.

## Что напрашивается (на будущее, не реализовано)

- Сделать цвет **детерминированным** от имени традиции (hash → HSL в пастельном
  диапазоне) — убирает недетерминизм, проблему контраста и, при желании, само
  хранение.
- **Цвет традиции как градиент внутри цвета её макро-ареала** (гипотеза). Вместо
  плоского случайного hue на традицию — брать **базовый цвет макро-ареала** (те же
  ~12 тонов, что в §7 `REGION_COLORS`) и разводить традиции внутри него по светлоте/
  насыщенности (шаг по L/S в HSL или позиция на короткой градиентной шкале ареала).
  Тогда цвет становится **осмысленным, а не декоративным**: родственные традиции
  (Greek/Roman/Norse под Indo-European) сразу читаются как один семейный тон, а
  ареал узнаётся по hue во всех разделах. Детерминированно: `hue = area_base(major)`,
  `L/S = f(index традиции внутри ареала)` — снимает и недетерминизм §6.1, и проблему
  контраста §6.3 (разводим внутри узкого, заведомо различимого диапазона), и заодно
  **сшивает три классификации** — одна палитра ареалов кормит и цвет традиции, и
  `REGION_COLORS`, и гео-ось. Требует стабильного порядка традиций внутри ареала
  (алфавит по имени) и запаса светлот на самый крупный ареал (Indo-European — 6
  традиций). Естественно ложится поверх продакшенизации 12 макро-ареалов.
- **Один** дефолт-цвет и одна точка извлечения цвета традиции на фронте.
- Убрать вторую палитру в embeddings и/или денормализацию в catalog (оставить
  один канал — `traditionInfo`).

## Обновление — единый дефолт «нет цвета» (реализовано)

Пункт §6.4 закрыт: четыре «заливочных» дефолта, означавшие «у категории нет
цвета» (`#6b7280`, `#334155`, `#888888`, `#aaaaaa`), сведены к одному источнику —
CSS-токену `--category-none` (`app.css`) и JS-константе `CATEGORY_NONE`
(`core.js`), значение `#6b7280`. Оба фронтовых канала теперь на нём: деревья,
corpus info-dot, маркеры Atlas, Plotly-трейсы, узлы графа, fallback в
`getTraditionColor`. Бэкенд (`get_catalog_documents`) уже использовал то же
`#6b7280`, так что расхождения нет. Оставлены как **другая семантика**: `#555`
(цвет текста score, рамка узла графа) и `#94a3b8` (рамка маркера) — это текст/
рамки, а не «нет цвета»; их место у `--muted` / `--border`, но менять видимый цвет
не стали.

Пункт §5.4 тоже закрыт: **вторая палитра (tab10) в embeddings убрана**. `getColorMap`
теперь красит каждую традицию её собственным цветом, а при отсутствии — тем же
`CATEGORY_NONE`, что и весь UI; отдельной цветовой схемы больше нет. Видимый эффект
минимален (только бесцветные традиции, по сути ведро «Unknown», становятся серыми
вместо tab10) и заодно уходит скрытая нестабильность — раньше цвет бесцветной
традиции зависел от её позиции в списке (`index % 10`) и мог совпасть с реальным
цветом другой традиции. Детерминированный цвет от имени — по-прежнему не тронут
(отдельная, более крупная правка).
